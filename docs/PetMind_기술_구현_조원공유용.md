## 1. 프로젝트 개요

PetMind는 보호자가 집을 비운 동안 발생한 반려견의 소리와 주변 영상을 기록하고, 과거 관찰 기록과 보호자 의견을 함께 분석해 상황 확인을 돕는 시스템이다.

### 해결하려는 문제

- 보호자가 외출 중 발생한 상황을 직접 확인하기 어렵다.
- 소리나 짧은 움직임만으로 감정·질병을 단정하면 오판 가능성이 있다.
- 반려견마다 평소 행동과 반응이 달라 일반적인 AI 답변만으로는 부족하다.
- AI 결과가 나와도 어떤 원본과 과거 기록을 근거로 했는지 확인하기 어렵다.

### 프로젝트의 접근 방법

1. 반려견 주변의 음성과 영상을 수집한다.
2. 음성 AI로 개 소리일 가능성이 높은 구간을 찾는다.
3. 감지 당시의 원본 음성과 전후 영상을 보존한다.
4. 같은 반려견의 과거 관찰과 보호자 의견을 검색한다.
5. 검색 결과를 바탕으로 외출 설명이나 케어 제안을 생성한다.
6. 보호자가 원본 근거를 확인하고 최종 판단한다.

### 핵심 원칙

- AI 결과는 **후보 정보**이며 자동 진단이 아니다.
- 모델 점수, 원본 자료, 보호자 의견을 분리해 저장한다.
- 근거가 부족하거나 분석에 실패한 경우 그 사실을 표시한다.
- 케어 행동은 AI가 바로 실행하지 않고 보호자의 승인을 받는다.

## 2. 전체 시스템 구성

```text
Raspberry Pi 또는 파일 입력
        ↓
음성·영상 수집과 전처리
        ↓
음성 LSTM 분석
        ↓
FastAPI 백엔드
        ↓
SQLite 기록 저장
        ↓
MCP 기반 과거 기록 검색
        ↓
Gemini 또는 규칙 기반 설명
        ↓
Flutter 보호자 화면
```

| 구성 요소 | 담당 역할 |
|---|---|
| Raspberry Pi | 카메라·마이크 입력 수집, 서버 작업 및 장치 명령 확인 |
| FFmpeg | 영상·음성 분리, 구간 버퍼와 사건 영상 생성 |
| 음성 LSTM | 5초 음성 창별 개 소리 후보 점수 계산 |
| FastAPI | 앱·모델·DB·장치를 연결하는 REST API 제공 |
| SQLite | 관찰, 외출, 음원, 영상, 의견, 제안 및 명령 저장 |
| MCP | AI가 사용할 과거 기록을 읽기 전용 도구로 제공 |
| Gemini | 검색된 기록에 근거한 설명과 케어 문장 생성 |
| Flutter | 보호자가 결과와 원본 근거를 확인하는 웹 화면 |

## 3. 사용 기술

### 3.1 Python

백엔드, AI 추론, 데이터 처리, 장치 프로그램과 평가 스크립트를 Python으로 구현했다.

선택 이유:

- PyTorch 기반 AI 모델 개발이 쉽다.
- FastAPI로 API 서버를 구성할 수 있다.
- 음성·영상 처리 라이브러리가 풍부하다.
- Windows 개발 PC와 Raspberry Pi에서 모두 사용할 수 있다.
- 분석, 서버, 테스트를 같은 언어로 관리할 수 있다.

### 3.2 FastAPI와 Uvicorn

FastAPI는 Flutter, AI 모델, SQLite 및 Raspberry Pi 사이의 요청을 처리한다. Uvicorn은 FastAPI 애플리케이션을 실행하는 ASGI 서버다.

음원 업로드 예시:

```text
Flutter에서 WAV 업로드
→ FastAPI가 파일 크기·형식·동의 정보 확인
→ 음성 모델 실행
→ 관찰 및 분석 결과를 SQLite에 저장
→ 결과를 JSON으로 Flutter에 반환
```

### 3.3 SQLite와 SQLAlchemy

SQLite는 별도의 DB 서버 없이 하나의 로컬 파일로 사용할 수 있어 단일 가정용 시제품에 적합하다. SQLAlchemy는 Python 객체와 DB 테이블을 연결하는 ORM으로 사용한다.

저장 대상:

- 반려견 프로필
- 관찰과 외출 세션
- 업로드 음원과 분석 결과
- 사건 영상 연결 정보
- 보호자 의견과 메모
- 케어 제안과 인용 근거
- 장치 명령 상태
- 저장·학습 동의와 원본 보존 상태

### 3.4 Flutter와 Dart

Flutter로 보호자용 웹 화면을 구현했다. 하나의 코드 기반으로 웹·모바일·데스크톱 확장이 가능하지만 현재 검증 중심은 웹이다. `http` 패키지로 FastAPI와 통신한다.

### 3.5 주요 라이브러리

| 기술 | 용도 |
|---|---|
| PyTorch | 오디오 LSTM 학습과 추론 |
| NumPy·SciPy | 수치 계산과 음성 처리 |
| SoundFile | WAV 읽기와 저장 |
| FFmpeg | A/V 입력, 음성 추출, MP4 구간 생성 |
| OpenCV | 보존된 영상 실험과 프레임 처리 |
| SQLAlchemy | DB 모델과 쿼리 관리 |
| Pydantic | API 요청·응답 검증 |
| MCP Python SDK | 기록 검색 도구 프로세스 구성 |
| pytest·flutter_test | 백엔드·AI·화면 회귀 테스트 |

## 4. 음성 분석 방법

### 4.1 분석 목적

음성 모델은 입력 구간을 다음 두 후보로 분류한다.

- `dog_candidate`: 개 소리일 가능성이 높은 구간
- `other_candidate`: 다른 소리일 가능성이 높은 구간

모델이 판단하지 않는 항목:

- 행복·불안·분노 등 감정
- 특정 반려견의 소리인지 여부
- 질병 또는 공격성
- 실제 짖음 횟수
- 정확한 발성 시작·종료 시점

### 4.2 입력 전처리

```text
WAV
→ 16kHz 신호
→ 5초 단위 분할
→ STFT
→ Mel 필터뱅크
→ Log-Mel Spectrogram
→ 평균·표준편차 정규화
→ LSTM 입력
```

#### 16kHz 샘플링

1초 동안 음성 파형을 16,000번 측정한다. 일반적인 동물 음향 패턴을 분석하면서 데이터 크기와 연산량을 제한하기 위한 설정이다.

#### 5초 분석 창

30초 음원은 대략 6개의 분석 창으로 나뉜다. 따라서 “개 소리 후보 창 3개”는 세 번 짖었다는 뜻이 아니라, 개 소리 가능성이 높은 5초 구간이 세 개라는 뜻이다.

#### STFT

음성을 짧은 시간 단위로 나누어 각 시점에서 강한 주파수를 계산한다. 이를 통해 파형의 크기뿐 아니라 시간에 따른 주파수 변화를 표현한다.

#### Log-Mel Spectrogram

STFT 결과를 Mel 주파수 축으로 변환하고 로그를 적용한 특징이다.

- 가로축: 시간
- 세로축: 주파수
- 값: 해당 시간·주파수의 에너지

### 4.3 LSTM 분류

LSTM은 이전 시점의 정보를 기억하며 순차 데이터를 처리하는 신경망이다. 시간에 따라 변하는 음성 패턴을 처리하기 위해 사용한다.

```text
Log-Mel 특징
→ LSTM 계층
→ 시간 정보 요약
→ 출력 계층
→ 개 소리 후보 점수
```

점수가 모델 체크포인트에 저장된 임계값 이상이면 `dog_candidate`가 된다. 점수는 확률처럼 보이지만 실제 환경에 완전히 보정된 확률이나 감정 신뢰도가 아니다.

### 4.4 에너지 후보와 LSTM 후보의 차이

| 구분 | 에너지 기반 후보 | LSTM 기반 후보 |
|---|---|---|
| 판단 기준 | 소리 크기 | 시간·주파수 패턴 |
| 장점 | 빠르고 모델 없이 실행 가능 | 단순 음량보다 개 소리 구분에 유리 |
| 한계 | 생활 소음도 감지 | 체크포인트 필요, 환경 변화에 민감 |
| 의미 | 소리가 발생한 후보 | 개 소리일 가능성이 있는 5초 창 |

두 수치를 분리해 “큰 소리가 났다”와 “개 소리 후보가 감지됐다”를 혼동하지 않도록 했다.

## 5. 감지 시점의 영상 저장

### 5.1 영상의 역할

현재 카메라는 행동을 자동 분류하기 위한 것이 아니다. 음성 감지 당시의 상황을 보호자가 직접 확인하는 원본 근거로 사용한다.

확인 가능한 예:

- 반려견이 실제 화면에 있었는가?
- 방문자나 외부 자극이 있었는가?
- 물체가 떨어지는 등의 생활 소음이었는가?
- 음성과 영상 상황이 일치하는가?

### 5.2 FFmpeg 버퍼 처리

```text
카메라·마이크 입력
→ 약 5초 단위 임시 MP4 생성
→ MP4에서 WAV 추출
→ 음성 LSTM 분석
→ 감지된 창의 앞뒤 구간 선택
→ 겹치는 사건 병합
→ MP4 생성·업로드
→ 관찰 ID와 연결
```

기본적으로 감지 창 앞 5초와 뒤 5초를 붙인다. 10~15초 구간에서 감지됐다면 약 5~20초 범위의 15초 사건 영상이 만들어질 수 있다.

연속 감지 구간은 중복 영상을 줄이기 위해 병합하고, 너무 긴 감지는 기본 최대 길이 단위로 나눈다. 임시 버퍼가 저장 용량 기준을 넘으면 수집을 중단한다.

### 5.3 실패와 누락 표시

| 상태 | 의미 |
|---|---|
| `camera_unavailable` | 카메라 입력을 사용할 수 없음 |
| `buffer_gap` | 필요한 앞뒤 영상 일부가 없음 |
| `encode_failed` | MP4 인코딩 실패 |
| `upload_failed` | 서버 업로드 실패 |
| 모델 미준비 | LSTM 체크포인트가 없거나 로딩 실패 |

영상이 없다는 사실을 “아무 일도 없었다”로 해석하지 않도록 실패 원인을 보존한다.

## 6. 외출 세션 방식

관찰을 외출 단위로 묶어 서로 다른 날이나 외출의 기록이 섞이지 않도록 한다.

```text
외출 시작
→ 음성·영상 수집
→ 관찰 기록 생성
→ 보호자 검토·의견
→ 귀가 및 외출 종료
→ 외출 요약과 과거 외출 비교
```

외출 세션에 포함되는 정보:

- 시작·종료 시각
- 입력 방식과 수집 세션 ID
- 분석된 음원과 총 분석 시간
- 에너지 기반 소리 후보 수
- 음성 LSTM 개 소리 후보 창 수
- 사건 영상과 원본 가용 상태
- 보호자 확인 의견
- 미분석 시간, 실패 및 누락 상태
- 이전 외출과 비교 가능한 항목

중복 원본 음원은 요약 수치에서 한 번만 집계하지만, 각각의 보호자 의견은 보존한다.

## 7. RAG와 MCP

### 7.1 RAG란?

RAG는 생성형 AI가 답변하기 전에 관련 자료를 검색해 근거로 사용하는 방법이다. Gemini가 알 수 없는 개별 반려견의 과거 기록을 DB에서 찾아 함께 전달한다.

```text
보호자 질문 또는 현재 관찰
→ 같은 반려견의 기록으로 제한
→ 기간 조건 적용
→ 키워드·의미 검색
→ 관련 관찰·의견·케어 이력 선택
→ Gemini에 근거와 허용 ID 전달
→ 근거 ID가 포함된 설명 생성
```

### 7.2 검색 조건

1. 현재 반려견과 같은 `pet_id`
2. 현재보다 과거에 생성된 기록
3. 질문에서 요구한 날짜 또는 기간
4. 질문과 의미상 관련된 기록
5. 제한된 개수의 상위 근거

### 7.3 키워드 검색과 의미 검색

| 방식 | 설명 | 한계 |
|---|---|---|
| 키워드 검색 | 질문과 기록의 공통 단어를 검색 | 표현이 다르면 놓칠 수 있음 |
| 의미 검색 | 문장을 임베딩 벡터로 바꾸고 유사도 계산 | 외부 API와 설정 필요 |

의미 검색이 실패하면 키워드 방식으로 폴백하며 그 사실을 기록한다. `semantic_similarity`는 검색 유사도이지 관찰 판정의 신뢰도가 아니다.

### 7.4 MCP의 역할

Gemini가 데이터베이스에 직접 접근하지 않고, 별도의 읽기 전용 MCP 도구를 통해 필요한 정보만 받는다.

| MCP 도구 | 역할 |
|---|---|
| `search_observations` | 과거 관찰 검색 |
| `get_observation_stats` | 기간별 관찰 통계 |
| `get_care_history` | 이전 케어 제안과 이력 조회 |
| `get_outing_facts` | 특정 외출의 사실과 근거 조회 |

장점:

- AI가 DB를 임의로 수정하지 못한다.
- 어떤 도구와 근거를 사용했는지 추적하기 쉽다.
- 검색, 집계, 생성 책임을 분리할 수 있다.

## 8. Gemini와 규칙 기반 폴백

### 8.1 Gemini 제공자

Gemini에는 현재 관찰, 검색된 과거 기록, 보호자 의견, 관찰 통계, 이전 케어 이력과 허용된 근거 ID를 전달한다.

서버는 Gemini가 반환한 인용 ID가 실제 검색 결과에 포함됐는지 검사한다. 허용되지 않은 ID를 사용하거나 호출이 실패하면 해당 출력을 그대로 신뢰하지 않는다.

### 8.2 규칙 기반 폴백

```text
Gemini 정상
→ Gemini 결과와 인용 표시

Gemini 호출·검증 실패
→ 규칙 기반 템플릿 결과
→ 폴백 사유 표시

검색 근거 부족
→ 근거 부족 상태 표시
```

API 키가 없어도 기본 흐름을 시연할 수 있고, 화면에서는 `gemini`, `rule`, `rule-fallback`을 구분한다.

## 9. 귀가 및 하루 요약 생성

귀가 설명의 수치까지 Gemini가 자유롭게 생성하지 않도록 역할을 분리했다.

```text
서버
→ 중복 음원 제외
→ 총 분석 시간 계산
→ 에너지 후보 집계
→ LSTM 후보 창 집계
→ 실패·누락 상태 계산

검색·Gemini
→ 질문과 관련된 사실·근거 ID 선택

서버
→ 검증된 수치와 선택 근거로 문장 렌더링
```

이 방식은 생성형 AI가 잘못된 숫자를 만들어낼 위험을 줄인다. 다만 케어 제안은 검색 근거를 바탕으로 Gemini가 자유 문장을 생성하므로 문장 전체의 의학적·인과적 정확성이 입증된 것은 아니다.

## 10. 보호자 의견과 데이터 동의

개인 기록 저장과 공통 모델 학습 동의를 분리한다.

| 동의 | 의미 |
|---|---|
| 개인 기록 저장 | 해당 가정의 관찰 근거로 원본을 보관 |
| 공통 모델 학습 참여 | 검수 후 모델 개발 자료로 사용할 수 있음 |

사용자가 할 수 있는 작업:

- 분석 결과와 원본 음원 확인
- 실제 개 소리 여부 의견 입력
- 메모 작성
- 확인 추천 큐 검토
- 학습 참여 동의 변경·철회
- 원본 파일 삭제
- 보관·만료 상태 확인

학습 동의가 있어도 자동으로 모델을 재학습하거나 배포하지 않는다. 검수된 자료만 별도로 내보내는 구조다. 이미 학습에 사용된 데이터를 모델에서 역으로 제거하는 기능은 구현하지 않았다.

## 12. 보호자 승인 기반 장치 명령

AI가 케어 제안을 만들더라도 장치 명령을 즉시 실행하지 않는다.

```text
케어 제안 생성
→ 보호자가 내용과 근거 확인
→ 보호자가 승인
→ 서버가 장치 명령 생성
→ 장치가 명령 조회
→ 수신 상태 보고
→ 완료 또는 실패 보고
```

대표 상태:

```text
requested → acknowledged → completed
                         └→ failed
requested → timed_out
```

장치는 명령 ID를 로컬 SQLite 캐시에 저장해 동일 명령의 중복 실행을 줄인다. 현재 `completed`는 가상 장치 처리 완료를 의미하며 실제 스피커 음악 재생을 뜻하지 않는다.

## 13. Raspberry Pi 연결

Raspberry Pi의 역할:

- 카메라·마이크 입력 수집
- 자동 외출 작업 조회
- 서버와 시각 차이 확인
- 수집 상태 heartbeat 전송
- 승인된 장치 명령 처리

무거운 AI 추론은 Pi가 아니라 PC의 FastAPI 서버에서 수행한다.

```text
Raspberry Pi
→ SSH 역방향 터널
→ PC의 127.0.0.1 FastAPI
→ AI 추론·DB 저장
```

자동 외출 시작과 heartbeat에서 PC·Pi 시각 차이와 왕복 지연을 확인한다. 기준 2초를 넘으면 `clock_mismatch`로 기록하고 수집을 시작하지 않거나 중단한다.

이 검사는 잘못된 기록 시각을 줄이기 위한 것으로 실제 카메라와 마이크의 A/V 동기화 정확도까지 보증하지 않는다.

현재 서버는 로컬 주소와 로컬 웹 Origin을 중심으로 제한한다. `pet_id`와 장치 작업 토큰은 완전한 사용자·장치 인증이 아니므로 서버를 인터넷이나 공용 LAN에 직접 공개하면 안 된다.

## 14. 테스트 및 성능 평가

### 14.1 음성 모델 평가

ESC-50과 FSD50K 공개 음원을 이용했다.

| 지표 | 의미 |
|---|---|
| 정밀도 | 개 소리라고 예측한 결과 중 실제 개 소리 비율 |
| 재현율 | 실제 개 소리 중 모델이 찾아낸 비율 |
| F1 | 정밀도와 재현율의 조화 평균 |
| 혼동행렬 | TP·FP·FN·TN 개수 |

문서에 기록된 FSD50K 120개 평가 결과:

| 지표 | 결과 |
|---|---:|
| 정밀도 | 94.4% |
| 재현율 | 28.3% |
| F1 | 43.6% |

개 소리라고 표시한 결과는 비교적 정확했지만 실제 개 소리 60개 중 43개를 놓쳤다. 따라서 정밀도 94.4%를 전체 정확도 94.4%로 설명하면 안 된다.

### 14.2 RAG 평가

자체 작성 질문을 이용해 필요한 근거가 상위 5개 결과에 포함되는지 `Recall@5`로 확인했다.

```text
Recall@5
= 필요한 근거가 검색 결과 상위 5개 안에 포함됐는가
```

자체 질문 세트에서 결과가 개선됐지만 질문들이 개발에 사용됐으므로 독립적인 실제 사용자 성능으로 해석하지 않는다.

### 14.3 시스템 검증

- Python 단위·통합 테스트
- FastAPI 요청·응답과 DB 보존 테스트
- 음성 전처리·LSTM 테스트
- MCP stdio 프로세스 호출 테스트
- Gemini 실패 및 잘못된 인용 폴백 테스트
- 장치 완료·실패·중복·시간초과 테스트
- FFmpeg 사건 영상 생성·재생 테스트
- Flutter 위젯 테스트와 정적 분석
- Flutter 웹 릴리스 빌드

최신 상태 문서에는 Python 139개, Flutter 21개 테스트 통과가 기록되어 있다. 테스트 수는 코드 변경에 따라 달라질 수 있으므로 발표 직전에 같은 명령으로 다시 검증해야 한다.

## 16. 현재 한계와 후속 과제

### 모델과 데이터

1. 음성 LSTM의 외부 데이터 재현율이 낮다.
2. 실제 가정에서 장기간 수집한 독립 평가 자료가 부족하다.
3. 특정 반려견에 대한 개인화 정확도를 검증하지 않았다.
4. 모델이 놓친 소리는 사건 영상으로 보존되지 않는다.
5. 케어 제안의 실제 효과나 의학적 타당성을 검증하지 않았다.

### 장치와 운영

1. 실제 Pi 카메라·마이크의 장시간 운용은 미검증이다.
2. 실제 장비의 음성·영상 동기화 오차를 측정하지 않았다.
3. 네트워크 단절 후 완전한 오프라인 재전송이 없다.
4. 수집 프로세스의 자동 재연결·재시작이 제한적이다.
5. 물리 스피커 음악 재생은 연결하지 않았다.

### 서비스와 보안

1. 현재 `pet_id`는 사용자 인증이 아니다.
2. 로컬 단일 가정 시제품을 전제로 한다.
3. 외부 사용자 수집 전 인증과 사용자별 접근 제어가 필요하다.
4. 원본 음성·영상과 개인 기록에 대한 운영 수준의 보안 정책이 필요하다.
5. 학습에 이미 반영된 데이터를 모델에서 제거하는 역학습은 구현하지 않았다.

### 다음 우선순위

1. 다양한 실제 생활 소음과 개 소리 자료로 독립 평가
2. 음성 LSTM의 낮은 재현율 개선
3. 실제 Pi 마이크·카메라와 A/V 시간 오차 측정
4. 장시간 수집, 장애 복구 및 저장 공간 관리 검증
5. 사용자 인증과 가정별 데이터 접근 제어
6. 장기 기록과 실제 보호자 피드백을 이용한 RAG 품질 평가
